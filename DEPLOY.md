# Разворачивание с нуля — инструкция для агента

Написано для того, чтобы **любой Claude-сессии без памяти о прошлых разговорах** хватило этого
файла, чтобы поднять `vpnctl` с нуля: свежий сервер + свежий мак, любой хостер, любая ОС мака
(Intel/Apple Silicon). Каждый пункт «грабли» ниже — реально наступили в процессе разработки
этого инструмента, не гипотетические.

Читай целиком перед первым действием — многие грабли экономят часы, если знать о них заранее.

## 0. Что нужно от пользователя до старта

Спроси, если не дано:

1. **SSH-доступ к серверу** — IP, пользователь (обычно `root`), пароль или уже готовый ключ.
   Если пароля/ключа нет — сначала помоги пользователю их получить у хостера.
2. **Есть ли домен** для этого сервера, или работаем по голому IP. Влияет на выбор
   Reality/TLS-с-доменом/TLS-без-домена (см. §3).
3. Сервер уже **новый и чистый**, или на нём что-то уже стоит (другая панель, другой VPN)?

Не гадай про хостера/ОС — команды ниже написаны под Ubuntu/Debian (`apt`, `systemd`, `ufw`).
Если ОС другая — адаптируй по аналогии, явно предупреди пользователя, какие шаги менял.

## 1. Сервер: базовая защита

```bash
ssh root@<IP>
# сменить пароль, если это первый вход после выдачи хостером
passwd
```

На маке — сгенерировать ключ и поставить на сервер:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/vpn_<IP-без-точек-или-своё-имя> -N ""
ssh-copy-id -i ~/.ssh/vpn_<имя>.pub root@<IP>
```

На сервере — отключить вход по паролю, поставить фаервол:

```bash
cat >/etc/ssh/sshd_config.d/99-key-only.conf <<'EOF'
PasswordAuthentication no
EOF
systemctl restart sshd

apt update && apt install -y ufw fail2ban
ufw allow OpenSSH
ufw allow 80/tcp
ufw allow 443/tcp
ufw --force enable
systemctl enable --now fail2ban
```

**Грабля:** дешёвые хостеры иногда троттлят новые TCP-подключения — SSH может зависать на
обмене баннером ("Connection timed out during banner exchange" / "banner exchange"). Это не
твоя ошибка и не бан — подожди 10–30 секунд и повтори команду. В коде это учтено
(`add_inbound.py`, `client_admin.py` и другие серверные скрипты рассчитаны на повторный запуск).

## 2. 3x-ui / Xray

```bash
bash <(curl -Ls https://raw.githubusercontent.com/MHSanaei/3x-ui/master/install.sh)
```

Установщик сам сгенерирует логин/пароль панели, секретный путь (webBasePath) и порт — сохрани
всё это **только локально**, не в git (см. §7). Проверь:

```bash
/usr/local/x-ui/x-ui setting -show
```

Открой порт панели в ufw:

```bash
ufw allow <порт_панели>/tcp
```

### Грабля: прямая запись в sqlite-базу панели НЕ РАБОТАЕТ

Соблазн — писать `inbounds`/`clients` прямо в `/etc/x-ui/x-ui.db` (sqlite). **Так делать нельзя.**
Проверено многократно вживую: inbound, добавленный прямой записью в БД, слушает порт, отдаёт
валидный TLS-хендшейк, но VLESS-аутентификация не проходит — даже когда сервер подключается сам
к себе (`127.0.0.1→127.0.0.1`). То же с multi-user клиентами Shadowsocks — список `clients` в БД
просто игнорируется движком.

Причина: панель прогоняет конфиг через собственную Go-логику (`Heal*`/`Strip*` в
`internal/database/model/model.go` у 3x-ui) при сохранении через веб-интерфейс или API. Прямая
запись в БД эту обработку пропускает — получается формально валидный, но нерабочий JSON.

**Правильный способ — HTTP API панели**, который прогоняет то же самое, что и веб-интерфейс:

```bash
# токен (не хранится в открытом виде на сервере — перевыпускается)
/usr/local/x-ui/x-ui setting -getApiToken
```

```bash
curl -s -X POST "http://<IP>:<порт_панели>/<секретный_путь>/panel/api/inbounds/add" \
  -H "Authorization: Bearer <ТОКЕН>" \
  -H "Content-Type: application/json" \
  -d '{
    "remark": "main",
    "enable": true,
    "port": 443,
    "protocol": "vless",
    "settings": "{\"clients\":[{\"id\":\"<UUID>\",\"flow\":\"xtls-rprx-vision\",\"email\":\"me\",\"limitIp\":0,\"totalGB\":0,\"expiryTime\":0,\"enable\":true,\"tgId\":0,\"subId\":\"<16 hex>\",\"reset\":0}],\"decryption\":\"none\",\"fallbacks\":[]}",
    "streamSettings": "{...см. §3...}",
    "sniffing": "{\"enabled\":true,\"destOverride\":[\"http\",\"tls\",\"quic\",\"fakedns\"]}"
  }'
```

**Грабля внутри грабли:** поле `tgId` должно быть числом `0`, а не пустой строкой `""` —
иначе панель ответит `json: cannot unmarshal string into Go struct field .0.tgId of type int64`.

**Грабля:** панель по умолчанию часто поднимается на **HTTP, не HTTPS** — если curl с `https://`
даёт `SSL_ERROR_SYSCALL`/зависание, попробуй `http://`.

Проверять живым TCP+API — не полагаться на "команда не вернула ошибку". После создания inbound'а:
1. Открыть порт в ufw (`ufw allow <порт>/tcp` + `/udp`).
2. Проверить TCP-хендшейк с мака (`python3 -c "import socket; socket.create_connection(('<IP>', <порт>), timeout=8)"`).
3. Проверить реальным клиентом (см. §5) — не только TLS/TCP, а полный туннель с ответом от
   `https://api.ipify.org`.

Готовые обёртки в этом репозитории (`add_inbound.py`, `client_admin.py`) **исторически писали в
БД напрямую и это признанно нерабочий путь** для новых inbound'ов/clients на некоторых сборках
3x-ui — прежде чем полагаться на них для создания НОВОГО inbound'а, перепроверь тем же
трёхшаговым тестом выше. Для **чтения** состояния (`collect.py`/`remote_dump.py`, тоже sqlite)
проблем нет — ломается только запись.

## 3. Reality vs TLS — что выбрать

По умолчанию Reality привлекательнее (маскировка под реальный сайт, не нужен домен). Но:

### Грабля: Reality может не проходить хендшейк вообще ни с кем

На части сборок/версий Xray-core (встречено на 26.7.28) Reality-хендшейк не проходит даже
**сервер сам с собой** (`127.0.0.1→127.0.0.1`) — лог сервера пишет `REALITY: processed invalid
connection... handshake did not complete successfully`, клиент видит `received real certificate
(potential MITM or redirection)` или тихий таймаут. Проверено: не помогает ни смена ключей, ни
откат версии xray-core, ни фикс `minClientVer` (см. ниже) — причина не найдена, диагностика
заняла много времени. Не трать на это часы — **потрать 15 минут на решающий тест**:

```bash
# С САМОГО СЕРВЕРА, не с мака — исключает сеть между клиентом и сервером
# как переменную. Если это не проходит — переключайся на TLS, не копай дальше.
```

Собери минимальный vless+reality outbound-конфиг для xray-core (или sing-box), укажи
`address: 127.0.0.1`, запусти на сервере локально, проверь curl через SOCKS. Не проходит —
переключайся на схему ниже.

**Сопутствующая, но самостоятельная проблема:** 3x-ui может хранить поле как `minClient`/
`maxClient` (без `Ver`), а Xray-core (см. исходники, `infra/conf/transport_security.go`) читает
**только** `minClientVer`/`maxClientVer`. Из-за опечатки в имени поля значение никогда не доходит
до xray-core, и он сам подставляет дефолт `26.3.27` — любой клиент, не умеющий сообщить о себе
такую же версию xray-core (весь не-xray-core мир — sing-box и другие независимые реализации),
получает отказ. Чинится через тот же HTTP API — выставить `minClientVer` явно, например `"0.0.0"`.
**Это стоит почини'ть в любом случае**, но само по себе оно может не решить проблему выше.

### Схема без Reality — VLESS + TLS, настоящий сертификат без домена

Если домена нет — раньше единственным вариантом был самоподписанный сертификат
(`allowInsecure` у клиента). **Не обязательно.** Let's Encrypt теперь умеет короткоживущие
(~7 дней) сертификаты прямо на IP-адрес через ACME-профиль `shortlived`:

```bash
curl https://get.acme.sh | sh -s email=<любой-валидный-email>
# ВАЖНО: если ACME_DEFAULT_CA не задан явно, acme.sh может по умолчанию идти в ZeroSSL —
# у него частые проблемы с анонимной EAB-регистрацией для IP-сертификатов (invalidContact).
~/.acme.sh/acme.sh --server letsencrypt \
  --issue --standalone -d <IP> \
  --cert-profile shortlived \
  --accountemail <email>

~/.acme.sh/acme.sh --install-cert -d <IP> \
  --cert-file /etc/x-ui/tls/vpn-le.crt \
  --key-file /etc/x-ui/tls/vpn-le.key \
  --reloadcmd "systemctl restart x-ui"
```

**Грабля:** `--cert-profile shortlived` нужно передать **на `--issue`**, не только на
`--install-cert` — иначе профиль не сохранится в `~/.acme.sh/<IP>_ecc/<IP>.conf` как
`Le_Certificate_Profile`, и следующее автопродление (`acme.sh --cron`, обычно в crontab)
уйдёт на дефолтный профиль, который **не разрешает IP-идентификаторы**, упадёт с
`rejectedIdentifier: Default profile does not permit IP address identifiers` — **молча**,
если вывод cron не перенаправлен в файл. Сертификат живёт 7 дней — если это не заметить,
через неделю VPN просто перестанет работать. Обязательно:

```bash
crontab -l  # проверить, что задача acme.sh есть и пишет НЕ в /dev/null
# если пишет в /dev/null — исправь на файл:
# 16 1,7,13,19 * * * "/root/.acme.sh"/acme.sh --cron --home "/root/.acme.sh" >> /var/log/acme-renew.log 2>&1
```

streamSettings для inbound'а с этим сертификатом (передать через API, см. §2):

```json
{
  "network": "tcp",
  "security": "tls",
  "tlsSettings": {
    "serverName": "",
    "minVersion": "1.2",
    "maxVersion": "1.3",
    "certificates": [{"certificateFile": "/etc/x-ui/tls/vpn-le.crt", "keyFile": "/etc/x-ui/tls/vpn-le.key"}],
    "alpn": ["http/1.1"],
    "settings": {"allowInsecure": false, "fingerprint": "chrome"}
  }
}
```

`allowInsecure: false` — сертификат настоящий, `insecure` клиенту не нужен (проверено живым
подключением). В `servers.json` соответствующему серверу оставь `"tls_insecure": false`.

## 4. Мак: клиент

```bash
brew install sing-box
git clone <этот-репозиторий>
cd vpnctl
cp servers.example.json servers.json    # заполнить своими значениями
cp setup.example.md setup.md            # свой журнал настройки, не коммитится
python3 collect.py                      # собрать состояние с сервера
```

Проверка без root:

```bash
./vpn старт
curl --socks5 127.0.0.1:2080 https://api.ipify.org   # должен показать IP сервера
./vpn стоп
```

### Грабля: кириллица в bash-идентификаторах

Bash в macOS (даже свежий) **не принимает кириллицу слева от `=`** ни в обычном присваивании
(`переменная=значение`), ни в `local переменная=...`, ни в `read -ra переменная <<<`. Все три
формы дают синтаксическую ошибку (`not a valid identifier`). Если пишешь новый bash-код в этом
репозитории (стиль — имена функций и комментарии на русском) — **имена функций и строковые
литералы можно на русском, но все настоящие переменные — латиницей.** Перед коммитом:

```bash
grep -nE '^\s*[а-яА-ЯёЁ_][а-яА-ЯёЁ0-9_]*=|local\s+[а-яА-ЯёЁ]|read -ra [а-яА-ЯёЁ]' <файл>.sh
```

Пусто — чисто.

### Грабля: `pkill`/`kill` не гарантирует немедленную смерть процесса

Отправка SIGTERM не означает, что процесс уже мёртв — если следующая команда (`старт`) проверяет
`pgrep` сразу после `стоп`, она может увидеть ещё живой умирающий процесс и решить, что "уже
запущен", ничего не сделав. Нужно **дождаться** (поллинг `pgrep` в цикле с коротким `sleep`)
перед тем, как считать остановку завершённой.

### Грабля: пул подключений sqlite при итерации + записи одним курсором

Если код итерирует строки из `cursor.execute("SELECT ...")` **и одновременно** делает
`UPDATE`/`DELETE`/`INSERT` тем же курсором внутри цикла — итерация обрывается после первой же
изменённой строки (курсор sqlite3 в Python не терпит мутации во время активного `SELECT`).
Сначала `.fetchall()`, потом цикл с записью по сохранённому списку.

### Грабля: `/proc/net/tcp` не видит IPv6/dual-stack слушателей

Если пишешь скрипт присмотра/диагностики на сервере, который проверяет "слушает ли порт N" через
`/proc/net/tcp` — учти, что многие сервисы (включая xray) слушают на `*:port`, это dual-stack
IPv6-сокет, и такая запись есть **только в `/proc/net/tcp6`**, не в `/proc/net/tcp`. Проверяй оба
файла, и фильтруй состояние `0A` (LISTEN) — иначе исходящие соединения тоже засчитаются как
"порт слушает".

## 5. Проверка реальным клиентом — не только "команда не упала"

TCP-хендшейк и даже TLS-хендшейк могут проходить успешно **и при этом сам туннель не работает** —
дошли только до транспортного уровня, не до VLESS-аутентификации внутри него. Единственная
надёжная проверка — реальный сквозной запрос через прокси:

```bash
curl --socks5 127.0.0.1:2080 https://api.ipify.org
```

Ответ должен быть IP **сервера**, не твоего провайдера и не пусто/таймаут. Если хочешь
независимо от sing-box проверить конкретно серверную часть — поставь `xray-core` через Homebrew
(`brew install xray`) и собери минимальный клиентский конфиг с теми же параметрами — так можно
отделить "проблема в моём клиенте" от "проблема на сервере".

## 6. Firewall на каждый новый inbound

Устанавливая 3x-ui через типовой скрипт, `ufw` обычно открывает только 22/80/443 (плюс порт
панели, если установщик сам добавил правило). **Любой новый порт нужно открывать явно**:

```bash
ufw allow <порт>/tcp
ufw allow <порт>/udp
```

Забыть этот шаг — самая частая причина "inbound создан, слушает, но клиенты не подключаются".

**Грабля:** прежде чем выбирать порт для нового inbound'а — убедись, что он **свободен** и не
занят чем-то ещё (другой inbound, морда, панель). Xray не запустится вообще (провалит **все**
inbound'ы разом), если хотя бы один порт уже занят — `bind: address already in use` в логе
(`journalctl -u x-ui`). Проверка перед созданием: `ss -tln | grep :<порт>` на сервере.

## 7. Секреты — что никогда не коммитить

- Пароль/логин панели, API-токен, секретный путь панели (webBasePath)
- Приватный SSH-ключ и его путь, если путь содержит IP/идентифицирующую информацию
- UUID клиентов, PSK shadowsocks — это рабочие учётные данные VPN
- Готовая ссылка `vless://...`/`ss://...` — она содержит UUID/PSK целиком

Всё это — только в `setup.md` (локальный журнал, в `.gitignore`) и `servers.json` (тоже в
`.gitignore` — реальный IP и email клиента). В git идут только `*.example.*`-шаблоны с
плейсхолдерами. Перед `git add -A` в репозитории с реальными данными — грепни застейдженные
файлы на известные значения (пароль панели, токен, UUID) до коммита, не после.
